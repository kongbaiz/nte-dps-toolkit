P0033 [Finding Title] U-01｜高｜Native IPC 全局状态跨线程无同步
P0034 [Evidence Path] 位置：native/nte-mods-plugin/src/ipc_transport.cpp:36-43,139-156,549-566；native/nte-mods-plugin/src/plugin_runtime.cpp:617-675；native/nte-mods-plugin/src/mod_runtime.cpp:4481-4500
P0035 [Finding Body] 证据：ipc_pipe、ipc_event、OVERLAPPED、transport state、request/response 都是普通全局对象。游戏 viewport 线程在 program_lock 的 shared 区间执行 PumpLiveIpc；workspace worker 在 reload/reset 已释放 exclusive lock后调用 CloseIpc。ipc_dispatch_in_progress 只约束 viewport 回调，worker 不参与。因此 pump 与 close 可并发读写和关闭同一批对象。
P0036 [Finding Body] 影响：普通 C++ 对象的并发读写是语言级数据竞争；同时存在 use-after-close、HANDLE 复用、请求/响应破坏和宿主游戏崩溃风险。当前代码没有可证明的 IPC owner。
P0037 [Finding Body] 标记建议：将 transport 收敛为单一 owner 线程；worker 只投递 close/reload 意图。若保留跨线程访问，必须用覆盖完整状态机的同一锁或消息队列，并以 generation 绑定 HANDLE、event、OVERLAPPED、request/response。
P0038 [Finding Body] 后续验证：慢客户端持续请求并反复启停 IPC Mod；WinDbg 强制 PumpLiveIpc/CloseIpcPipe 交错，Application Verifier 开启 Handles/Locks。
P0040 [Finding Title] U-02｜高｜CancelIoEx 后立即清零并复用 OVERLAPPED
P0041 [Evidence Path] 位置：native/nte-mods-plugin/src/ipc_transport.cpp:139-164,187-218,266-271,290-315
P0042 [Finding Body] 证据：CloseIpcPipe 调用 CancelIoEx 后立即 DisconnectNamedPipe、CloseHandle、关闭 event，并把 ipc_overlapped 清零；下一 generation 又在 ResetIpcOverlapped 中复用同一静态结构。取消路径没有等待该 I/O 完成。Microsoft 文档明确说明 CancelIoEx 不等待取消完成，旧操作完成前不得复用关联 OVERLAPPED。
P0043 [Finding Body] 影响：即使没有 U-01 的双线程交错，单线程“客户端发送不足完整请求→1 秒超时→重连”也能进入违规路径。旧完成通知可能落入新 generation，造成状态错配、句柄竞态或崩溃。
P0044 [Finding Body] 标记建议：每个异步操作使用独立 RAII operation；CancelIoEx 后等待 GetOverlappedResult 对该具体操作完成/返回 ERROR_OPERATION_ABORTED，再释放 event、清零结构并启动下一 generation。
P0045 [Finding Body] 后续验证：客户端循环只写 1–1079 字节并保持超过 1 秒；检查取消后完成状态，不允许旧 completion 进入新 generation。
P0047 [Finding Title] U-03｜高｜Shadow vtable 未等待 dispatch quiescence 就释放
P0048 [Evidence Path] 位置：native/nte-mods-plugin/src/shadow_vtable_hook.cpp:125-218；native/nte-mods-plugin/src/plugin_runtime.cpp:511-545,911-983,1008-1035
P0049 [Finding Body] 证据：Remove 先尝试把对象 vptr 换回 original，随后无条件 VirtualFree shadow allocation。它没有 active-dispatch counter、epoch、hazard pointer、grace period 或宿主线程停顿证明；installed_ 也不参与 CPU 的虚调用分派。若可写性检查失败或 CAS 未恢复对象 vptr，allocation 仍会被释放。
P0050 [Finding Body] 影响：调用线程可能先读取 shadow vptr 后被抢占，管理线程恢复并释放表，调用线程再读取表项即访问已释放页。热重载、viewport 替换和 unwatch 都会触发，不只发生在 DLL 卸载。
P0051 [Finding Body] 标记建议：恢复对象 vptr 后把表放入 retired list，仅在所有潜在调用者跨过 grace period 后回收；若无法证明 quiescence，宁可在进程生命周期内保留小表。恢复失败时绝不能回收仍可能被对象引用的表。
P0052 [Finding Body] 后续验证：fake vtable 两线程压力测试 + PageHeap；另覆盖对象页暂时不可写时 Remove 不得留下悬空 vptr。
P0054 [Finding Title] U-04｜高｜Viewport hook 切换共用一个 original 指针
P0055 [Evidence Path] 位置：native/nte-mods-plugin/src/plugin_runtime.cpp:128-132,204-215,348-369,480-549
P0056 [Finding Body] 证据：两个 shadow hook 共用 original_viewport_tick。切换时先把全局 original 改为 candidate_tick，再安装新 hook，最后才移除旧 hook；回调又在校验 viewport 之前先调用全局 original。因此旧 viewport 可在窗口期执行 candidate_tick(old_viewport)。
P0057 [Finding Body] 影响：当新旧 tick 地址/对象布局不同，旧对象会进入错误实现，可能破坏状态或崩溃；地址相同则不触发，所以这是静态确认、条件触发的竞态。
P0058 [Finding Body] 标记建议：original 必须按 hook/object 绑定；detour 根据 viewport 查不可变 hook record。切换应先发布完整映射，旧记录只在 in-flight 归零后退休。
P0059 [Finding Body] 后续验证：使用两个 tick 地址和 magic 不同的 fake viewport 并发 handoff，断言旧对象从不进入新 tick。
P0061 [Finding Title] U-05｜高｜DllMain 在 loader lock 内加载、起线程、无限等待和卸载
P0062 [Evidence Path] 位置：native/nte-mods-plugin/src/nte_mods_plugin.cpp:9-21；native/nte-mods-plugin/src/dwmapi_proxy.cpp:27-59；native/nte-mods-plugin/src/plugin_runtime.cpp:1038-1111；native/nte-mods-plugin/nte-mods-plugin.vcxproj:53
P0063 [Finding Body] 证据：DLL_PROCESS_ATTACH 内经 InitializeDwmapiProxy 调 LoadLibraryW，并启动两个 CreateThread；DLL_PROCESS_DETACH 内 StopPluginRuntime 对 worker 执行 WaitForSingleObject(INFINITE)，随后 FreeLibrary。工程 RuntimeLibrary=MultiThreaded（静态 CRT），却调用 DisableThreadLibraryCalls，且忽略其结果。Microsoft 要求 DllMain 只做极简工作、禁止 LoadLibrary/FreeLibrary 与跨线程同步，并明确静态 CRT DLL 不得调用 DisableThreadLibraryCalls。
P0064 [Finding Body] 影响：显式卸载时 loader-lock 线程等待 worker，worker 的退出或依赖 DLL detach 又可能等待 loader lock，形成死锁；另有部分初始化、CRT/TLS 清理异常和加载卡死风险。
P0065 [Finding Body] 标记建议：DllMain 只记录 module handle；把真实 dwmapi 加载、runtime start/stop 放到 loader lock 外的一次性惰性或显式初始化协议；detach 不得无限等待，worker 自己拥有停止与卸载握手。
P0066 [Finding Body] 后续验证：在可终止的 HTGame.exe 测试宿主中 LoadLibrary→启动 worker→另一线程 FreeLibrary；用 Wait Chain Traversal/WinDbg 检查 loader lock。
P0068 [Finding Title] U-06｜高｜VirtualQuery 后解引用游戏对象存在 check/use 竞态
P0069 [Evidence Path] 位置：native/nte-mods-plugin/src/memory_access.cpp:50-68,85-123；native/nte-mods-plugin/src/plugin_runtime.cpp:244-274,617-675；native/nte-mods-plugin/src/mod_runtime.cpp:4496-4499
P0070 [Finding Body] 证据：ReadBytes 先 IsReadableRange(VirtualQuery)，再由 CopyBytes 逐字节解引用；后台 WatchModWorkspace 还会 ResolveViewport 并直接读取 local_players.data[0]。VirtualQuery 不会 pin 页面或对象，游戏线程可以在检查与读取之间释放、换页或复用对象。现有 per-program SEH 不覆盖后台 ResolveViewport 和 SamplePartyEffects。
P0071 [Finding Body] 影响：地图/角色/viewport 重建时可抛出未捕获 access violation；即便页面仍 committed，也可能读取跨 generation 的混合指针并把 hook 安装到已复用对象。
P0072 [Finding Body] 标记建议：尽量把 UObject 链解析放到宿主游戏线程稳定阶段；跨线程读取用最小 SEH copy 或 ReadProcessMemory 封装，并在整条链末做 generation/一致性复核。不要把 VirtualQuery 视为安全读取证明。
P0073 [Finding Body] 后续验证：Full Page Heap/Application Verifier 下高频地图与 viewport 重建；对 CopyBytes 设 first-chance AV。
P0075 [Finding Title] U-07｜中｜Class vtable 页保护恢复失败被忽略

P0077 [Finding Body] 证据：替换 class vtable entry 后，第二次 VirtualProtect 恢复 old protection 的返回值没有检查；只要 CAS 成功，函数就返回成功。
